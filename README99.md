# 库存接口连吃两天 401 之后：TG 号库存的拉取、下单、回调，字段表与验签我按三段摊开

自建面板接了两天，库存接口一直返回 401。面板是给运营组用的，左边切品类、右边看剩余量，底下挂一个下单按钮；我把 Key 抄进 .env，curl 试、Node 试、换 UA 再试，回来永远是同一行 401。最要命的是我当时没打响应体，只把状态码记进日志——等于对着"拒绝"两个字猜了两天。

第三天才想起把 body 完整打出来：`{"code":401,"msg":"sign expired, ts drift > 300s"}`。签名没过期，是我本地时间戳用了东八区，服务端只认 UTC，容忍窗口 300 秒，我这边整整漂了 8 小时。改成 UTC 秒级、重签一次，列表刷出来了。这件事留下一个习惯：**任何 401，先把响应体打全，再去怀疑 Key。**

之后我把整条链路拆成三段重写：拉取、下单、回调。这三段失败代价完全不同，混在一个函数里写，就一定会在重试上翻车。下面按三段讲，字段、限额、验签、退避都摊开。

## 一、先把流程图摊在纸上，三段各有各的脾气

```
[自有面板] --(1) GET /stock?ts&nonce&sign-----> [库存接口]
           <-- sku_id / price / stock / updated_at --

[自有面板] --(2) POST /order  sku_id qty idem_key --> [下单接口]
           <-- order_no / status=paid（平均 18 秒出号）--

[推送服务] --(3) POST /callback  X-Sign X-Ts X-Nonce --> [自有面板]
           验签 → 落库 → 回 200 → 再入队
```

读接口可以放心重试，写接口绝不能无脑重试，回调必须幂等——三句话定完，剩下的都是细节。我第一版把三段塞进一个重试装饰器，结果一次网络抖动重发了 3 次下单请求，扣了三次库存。这跟平台没关系，是我自己把"读"的容错套在了"写"上。

## 二、拉取：字段看懂，比会调接口重要

库存是实时快照，卖完自动下架，所以"现货 36""仅剩 7"是真的可售量，不是文案。你要接的就是这些数：

| 字段 | 类型 | 含义 | 我踩过的坑 |
| --- | --- | --- | --- |
| `sku_id` | int | 商品编号，1–8 对应首页八张商品卡 | 硬编码 id 后站点换排序，映射全错 |
| `cat` | string | TG 账号 / 流媒体 / 游戏 / AI 工具 | 靠 `cat` 分组报价，别自己维护分类表 |
| `price` | decimal | 当前标价，促销会浮动 | 小号 6.9、成品号 25.9、老号 68，梯度比值才是决策依据 |
| `stock` | int | 实时可售量 | 把它当"永久有货"，付完款才发现要等补货 |
| `sold` | string | 已售量，仅展示 | 拿来当热度参考可以，别拿来算余量 |
| `deliver` | string | 交付形式：csv / api | 小号 10 个起批，走 api 要提前说清 |
| `updated_at` | string | 快照时间 | 不记时间，就说不清这单为什么按旧价扣的 |

三个限额记牢：单次拉取上限 200 条，全站 1268 件要分 7 页；调用频率 1–2 次/秒起步，别把它当压测对象；面板侧缓存 60 秒足够，运营看的是趋势不是毫秒。想拿真实数对一遍，直接开 [当日在售的分类页](https://tlgrqs-hao.com) 数一遍商品卡，比对着文档猜字段靠谱。

翻页最容易出的错是拿 `stock>0` 当过滤条件——补货中的 SKU 会瞬间消失，第二次拉又出现，你的面板就会闪。正确做法是全量拉、本地标状态。

## 三、下单：五个动作，一个都不能省

1. **生成 `idem_key`**：业务侧唯一，用"批次号-序号"，别用时间戳。时间戳重试一次就变，等于没幂等。
2. **提交前查本地单**：同一 `idem_key` 已有 `order_no` 就直接返回，不重复打。
3. **带 `sku_id` + `qty` + `idem_key` 提交**，不做任何"猜规格"的动作，规格写错只能换号不能退。
4. **超时不要立刻重发**：超过 10 秒没响应，先按 `idem_key` 查单，确认没落地再重试一次。
5. **立刻落库 `order_no`**：30 天换号质保凭的就是这个号，丢了要跟客服扯很久。

下单成功不等于拿到号。付款后触发取号，平均 18 秒出号，30 秒内加密推送到订单页与邮箱，夜里也一样——所以回调没来的时候，先怀疑自己的网络和验签，不要手动补单。补单最直接的后果是同一个批次出两套号，对账表永远对不平。

超过 20 个要谈批次价，别按标价直接下。谈之前把品类、数量、交付字段一次说清，[报给客服的入口就在首页底部](https://tlgrqs-hao.com)，Telegram 和 Discord 双通道，平均 42 秒有人接。

## 四、回调：验签四步，顺序错了全白干

回调是唯一可信的"货已交付"信号。验签不是可选动作——你的面板是公网可达的，没有验签的 `/callback` 等于给所有人开了一个免费发货按钮。

1. **先拿 raw body**：用 `express.raw()` 之类保留原始字节，别先 `JSON.parse` 再序列化回去，空格和键序一变签名就废。
2. **取三个头**：`X-Sign`、`X-Ts`、`X-Nonce`，缺一个直接 400。
3. **算 HMAC**：`HMAC-SHA256(secret, X-Ts + X-Nonce + raw_body)`，用恒定时间比较，别用 `==`。
4. **校验时效与重放**：`X-Ts` 与本地时间差不超过 300 秒，`X-Nonce` 记进 Redis 五分钟，重复的直接丢。

验签过了才算进门，字段还得对得上：

| 回调字段 | 说明 | 处理要点 |
| --- | --- | --- |
| `order_no` | 平台订单号 | 主键，必须先落库再处理业务 |
| `idem_key` | 你下单时传的键 | 反查本地单，对不上就是串单 |
| `status` | paid / delivered / failed | 只认 delivered 当发货成功 |
| `tg_phone` | 手机号 | 别和日志混打，单独加密存 |
| `code_url` | 接码地址 | 一次性，用完即弃 |
| `two_fa` | 双因素凭据 | 和手机号分开存，别放同一张表 |
| `delivered_at` | 交付时间 | 30 天质保的起算参考 |

顺序只有一个正确答案：**验签 → 落库 → 回 200 → 入队处理**。先处理再回 200，对方等超时会重推，你处理两遍；回 200 再落库，掉电就丢单。我见过最贵的写法是在回调里同步调首登接口，一次超时把整批推送卡住。

## 五、重试：能重的不多，退避要带抖动

把错误码分成三类，代码里按类处理，别一个 `catch` 全重试。

| 错误码 | 含义 | 是否重试 | 处理 |
| --- | --- | --- | --- |
| 401 | 签名过期 / ts 漂移 | 重签一次 | 校准 UTC，仍失败说明密钥错 |
| 429 | 频率超限 | 重试 | 指数退避，压回 2 次/秒以内 |
| 5xx | 服务端异常 | 重试 | 1/2/4/8 秒退避，最多 3 次 |
| 409 | 重复下单 | 不重试 | 按 `idem_key` 查单取回原 `order_no` |
| 402 | 余额不足 | 不重试 | 充值后人工确认再下 |
| 超时 | 未知结果 | 不重试 | 先查单，再决定补不补 |

退避别用固定值。`min(2^n, 30)` 秒再乘一个 0.5–1.5 的随机抖动，能让一批并发请求散开，不至于在同一秒把 429 刷满。回调侧的重推同理：你回 200 慢了，对方重推，靠 `order_no` + `status` 幂等挡住就行。

## 六、接口跑通那天，我删掉了 12 行重试代码

那 12 行是我最初写的"失败就再打一次"，删掉之后链路反而稳了。原因很简单：扣库存是会留下痕迹的动作，任何自动重试都得先问一句"这一单到底落没落地"，而这个问题只有一个答案——查单。

现在这套面板的日常是这样：拉取每 5 分钟一次，只用来刷新剩余量和价格；下单只在运营点按钮时发生，`idem_key` 由批次号生成；回调落到 `orders` 表，验签失败的单独进 `rejected` 表留证。三条纪律挂在 README 上：一是只信回调，不信轮询出来的"看起来发了"；二是 `order_no` 必须落库，30 天内换号全靠它；三是字段以回调为准，文档写的和实际推的差一个字母，就以推的为准，改代码不改口头约定。

面板上现在有一排"现货 36""仅剩 7""现货 99+"，运营看到红字就知道该催单了。这些数字背后就是同一个接口，你把三段拆清楚，它就是个老实的数据源；混在一起写，它每天都能给你变出新花样。要复核对齐的话，[站点的商品卡和交付说明](https://tlgrqs-hao.com) 是最直接的参照，价格、库存口径、质保窗口都写在上面，比自己猜快得多。

接口这类活，跑通不算本事，跑半年不出重复单才算。
