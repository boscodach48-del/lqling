# 下了三遍还在 0%：电报网页版下载中断的七个真实原因、重试怎么接着下、一堆 (1) 副本怎么收场

上周三晚上十一点多，群里有人丢了一份 1.8G 的施工进度视频，我点了下载就去洗漱。回来一看进度条卡在 63%，Wi-Fi 图标上挂了个感叹号——路由器掉线重连了。我把网修好，点重试，进度条老老实实从 0% 开始爬。那一夜我一共点了三次，第二天硬盘里躺着三个东西：一个 63% 的坏文件、一个 4KB 的空壳、一个终于下完的完整版，加起来快 4 个 G，能用的只有一个。

事后我把这件事从头捋了一遍，才发现"下载中断"根本不是网络问题那么简单——重试被清零、副本越攒越多、名字撞在一起，是三条独立的毛病，只是经常一起发作。

## **一、先认清楚：中断分三种，待遇完全不同**

判断错了类型，后面所有操作都是白费力气。

**第一种是任务还在、只是停住了。** 下载列表里那条记录没消失，旁边有"继续"或"恢复"按钮。这种情况最省事，点一下就从断点接着走，浏览器内部还在用分段请求。

**第二种是任务被丢掉、重头再来。** 记录消失，或者重试后进度归零。这时候已经不是"断"了，是连接被中途掐断、浏览器放弃了原有上下文，之前那几个 G 的字节等于白跑。

**第三种是任务显示完成、文件其实是废的。** 双击打不开，或者只有几 KB。这种最坑，因为它不会报错，你在群里说"收到了"，打开才发现是坏的。

## **二、七种断法对照表：看屏幕上的那句话**

我把这半年攒下的截图归了归类，同一个现象在不同浏览器里的措辞不一样，但判断逻辑是相通的。

| 现象 | 屏幕上的原话 | 真实原因 | 处理动作 |
| --- | --- | --- | --- |
| 进度条回到 0% | 任务消失，重新出现一条同名记录 | 连接被重置，浏览器不保留断点 | 换客户端或换支持分段的工具，别在原页面反复点 |
| 停在中间不动 | Chrome 显示"已暂停"，旁边有继续箭头 | 只是暂停，不是失败 | 点"继续"，别点"重新下载" |
| 报网络错误 | "失败 - 网络错误" | 代理节点抖动、DNS 解析中途换了线路 | 关掉系统代理和代理类扩展，换网络重试 |
| 显示被拦 | "已阻止"或"已拦截" | 连续下多个文件触发浏览器的自动下载拦截 | 地址栏左侧站点权限里放开"自动下载" |
| 秒完成但很小 | 文件大小只有 2–8 KB | 中间设备返回了一个错误页，当成文件存了下来 | 开无痕窗口重下，或换个 DNS 再试 |
| 直接没动静 | 无报错、无任务 | 目标盘满了、目录没写权限、路径指向已拔出的 U 盘 | 把下载位置改回本地固定目录 |
| 客户端转圈 | 一直显示"正在连接"或"等待网络" | 客户端掉线，网页版和客户端会话不同步 | 退出重开客户端，从本地缓存恢复 |

表里"客户端转圈"那行值得多说一句：桌面客户端的下载和浏览器是两条独立通道。客户端掉线时看起来像卡死，其实文件可能已经躺在缓存目录里了，重开一次就能续上。

## **三、想让它接着下，八个动作按顺序做**

顺序别打乱，前面几步能省掉后面大部分无用功。

1. **先开下载列表看状态字。** Chrome 按 `Ctrl + J`，或者地址栏敲 `chrome://downloads`；Edge 是 `edge://downloads`；Firefox 是 `about:downloads`。看的是"已暂停""已中断""已阻止"这几个字眼，措辞不一样，含义差很远。
2. **只点"继续"，不要点"重新下载"。** 这两个按钮挨得很近，点错一次就等于把已有的进度扔了。列表项右边那个向下箭头展开才有"重新下载"，平时别去碰。
3. **确认这条链接认不认断点。** 会命令行的话，把文件地址套进去跑一句 `curl -I -H "Range: bytes=0-1" 文件地址`，返回 `206 Partial Content` 并带 `Content-Range` 头，说明支持从中间接；返回 `200` 就只能从头来。
4. **大文件改走桌面客户端。** 客户端的"设置 → 高级 → 下载路径"里把目录定死，下载面板里右键有"在文件夹中显示"。它按分块拉取，断了会自己重试，不像浏览器那样一次性把责任推给你。
5. **把代理相关的开关全关一轮。** 系统代理、浏览器里的代理扩展、加速器客户端，三个地方任一个在起作用都可能让长连接被掐。断点续传最怕的就是中途换了出口 IP。
6. **换目录，别留在系统盘。** 我踩过一次：目标目录是一个已弹出的移动硬盘盘符，下载静默失败，一点提示都没有。改回本地固定盘立刻恢复。
7. **用无痕窗口做对照实验。** 无痕里能正常下，问题就在扩展或缓存上；无痕里一样断，问题在线路或目标站点。
8. **收尾一定校验。** Windows 命令行跑 `certutil -hashfile 文件名 SHA1`，把结果和发送方给的值对一下；没有哈希就至少比大小。这一步能挡掉那 2KB 的假文件。

浏览器之间这些路径的差异，站上 [Chrome 浏览器使用建议](https://tlgrlf-web.com) 和 Edge 那一节是分开写的，权限位置不一样，照着点更省事。

## **四、`(1)` 不是故障，是浏览器在保你的命**

很多人看到 `合同 (1).pdf` 就以为是哪里出错了。恰恰相反——这是浏览器在拒绝覆盖同名文件。它发现目录里已经有一个 `合同.pdf`，就自动加序号另存一份。客户端也是同样的逻辑，同名不覆盖，直接多存一个。

问题不在生成副本，在于副本攒起来之后没人认账。我现在的做法是三步判定：

- **先看大小**，文件夹里按"大小"排序，几个字节的、明显偏小的先删；
- **再看时间**，`(1)` 通常比原件新，但下载中断留下的那个往往是旧的坏文件，时间新不代表内容对；
- **拿不准就算哈希**，两个文件各跑一次 `certutil -hashfile`，值一样就是同一份东西，留哪个都行，删一个。

同一份文件被群里三个人转发，也会在你这里变成三份。这种情况不用挨个下——看文件大小和上传时间，数值完全一致基本就是同一个文件；只在其中一条上点下载，其余的不用管。

## **五、手机端的重复更隐蔽**

手机上不会给你看 `(1)`。群里同一个视频被转发三次，你要是开着"设置 → 数据和存储 → 保存到相册"，相册里就静静躺着三份，而且大小一样、缩略图一样，你根本分不出来。

安卓的文件一般落在内部存储的 `Telegram/Telegram Documents`，iPhone 在"文件"App 的 Telegram 文件夹里。中断的表现也不一样：通知栏的进度条会直接消失，App 里那个文件重新变回云朵图标，看起来像从来没下过。想少存重复的，把"自动下载媒体"按网络类型分开设——流量下只留文档，图片视频留给 Wi-Fi。

## **六、两端同时点，等于自己跟自己抢**

同一账号在网页版和桌面客户端同时点同一个文件，是两条互不知情的通道，各自下一份、各自存一份。我干过这事，结果硬盘里多出两份一模一样的 800M 视频。

更常见的浪费是：网页版下到一半断了，你以为没下成，转头去客户端再下一遍。其实客户端有本地缓存，只要那份缓存还在，重开客户端点一次下载，它会从缓存里瞬间补齐，不需要重新走网络。这也是我一直建议大文件优先走客户端的原因。

判断缓存还在不在，去客户端设置里看存储占用；占着几百兆却找不到对应文件，多半就在缓存里。

## **七、断网不可怕，重下三遍才可怕**

这一年下来我最深的体会是：中断本身只损失一次进度，真正把时间烧掉的是"不知道发生了什么就重新点一遍"。三次重试，三次从零，硬盘里三份残骸，到头来连哪份是对的都说不上来。

所以我把动作固定成三个：断了下意识先看下载列表的状态字，只点"继续"；大文件一律交给客户端，路径提前定死；下完先比大小，拿不准就算哈希。三件事加起来不到两分钟。

要是你也被同一个文件反复折腾过，可以对着 [浏览器缓存清理指南](https://tlgrlf-web.com) 把残留的临时文件清一遍——那些 `.crdownload`、`.part` 结尾的残片，看着不起眼，占的空间往往比你以为的多。清干净了再下一次，进度条才会老老实实走完。
