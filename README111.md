# 网页版登录状态能撑多久？同一个号同一台机器，我记录到最长 41 天，最短隔夜就得重扫

出差一周回来那晚，我掀开笔记本，浏览器标签栏上还留着走之前那排页面，位置一动没动。点回那个标签，刷出来的却是中间一块二维码，配一行让我用手机确认的提示。

Tab 没关，我也没点过任何退出。第一反应是号出事了，抓手机进设备列表一看，这台笔记本还挂在那儿，最近一次活跃时间停在一周前。悬着的心放下来，新的疑问顶上来：那它凭什么自己把我请出去？

后面两周这事又发生了五六回，间隔完全对不上——有一次隔夜就掉，有一次活了一个多月。把每次的条件摊开记，才看清"能保持多久"这个问法本身有点偏：它不是一张固定的期限表，而是几个设置和时间习惯叠出来的结果。想对着界面一步步核的，[Telegram网页版中文使用指南](https://tlgrqs-web.com) 里会话和缓存那两节写得比我细；下面这些是我自己机器的记录。

## 计这个时的不是一只表，是三根指针

一根在服务端：这套登录凭证有寿命，从你扫码那一刻开始走，走到哪算到期由服务端说了算，本机看不到倒计时。第二根在浏览器：本地那份凭证要是被清掉、被扩展删掉、被无痕模式关窗带走，服务端那边还活着也没用，你照样得重扫。第三根是活跃度——长时间没人动它，到期判定就会提前落到你头上。

三根指针里任何一根先停，界面表现都一模一样：回到二维码。所以「我怎么又被踢了」这句话，答案往往不在 Telegram 那边，而在你这台机器过去一周怎么被使用。

## 七种情况，我记了三周

记录方式是每次掉线就在日历上标一笔，顺便写下当时的浏览器、开关状态和前一次打开的时间。样本不大，但足够看出量级差。

| 场景 | 观察到的保持时长 | 到期时的界面 | 备注 |
| --- | --- | --- | --- |
| 主力机 Chrome，浏览器长期不关，只合盖 | 41 天 | 刷新后直接落二维码，无任何提示 | 期间几乎每天会打开一次 |
| 同一台机器，出差 8 天完全没碰 | 8 天 | 回来首开就是二维码 | 机器相同，只差"多久没动" |
| 备用机 Edge，装了自动清 Cookie 的扩展 | 隔夜 | 每次都要重扫，两步验证也得重填 | 扩展在后台按天清，人察觉不到 |
| 无痕窗口里登录 | 关窗即失效 | 下次开窗直接二维码 | 干净，但等于每次都重登 |
| 公司 Firefox，勾了关闭时清除历史记录 | 每次关机 | 开机首开二维码 | 勾选项里默认带 Cookie |
| 家里 Safari，开着"阻止所有 Cookie" | 根本稳不住 | 登进去刷一下就弹回登录页 | 不是到期，是被拦了 |
| 每天换节点的那个星期 | 2 到 3 天 | 先转圈再掉，不像正常到期 | 手机端全程不受影响 |

第三行和第七行最容易被误判成"账号有问题"。前者是本地凭证被定时擦掉，后者是出口一直在跳，服务端看到的位置对不上就收紧。两种情况都不是账号坏了。

## 到期之前，界面是提醒过你的

它不会提前弹窗说"还有十分钟到期"，但有四个痕迹，按出现顺序排：

1. 顶部状态变成 `Connecting…` 或 `Updating…`，同时别的网站打开飞快——网络没问题，是这条连接在松。
2. 左侧聊天列表的更新时间停住，别人的新消息迟迟不进来，头像陆续变成灰色占位。
3. 发出去的消息旁边冒出红色感叹号，点一下提示 `Message couldn't be sent`。此时会话可能还活着，先别急着重扫。
4. 手动刷新，页面直接落到二维码上。到这一步才是真到期，前面三步都还有救。

第 3 步和第 4 步之间那段时间最值得利用：能刷新回聊天列表，说明凭证还在，只是连接断了，换个网络或等两分钟就能续上；一刷新就出二维码，那就是凭证没了，做什么都不如直接重登来得快。

## 想让它活得久，先关三个开关再谈习惯

七条动作按性价比排，前面三条几乎立刻见效。

1. **关掉"关闭所有窗口时清除数据"。** Chrome 在 `设置 → 隐私和安全 → 网站设置 → 查看权限和网站数据`，Edge 在 `设置 → Cookie 和网站权限 → 管理和删除 Cookie 和网站数据`，那个"关闭所有窗口时清除"的开关默认是关的，但装过清理类工具后会被打开。
2. **顺手看一眼 Cookie 白名单。** 同一层页面里把站点加进"允许使用 Cookie"，比全局放开安全得多。Chrome 近两年的版本把这块从"网站设置"挪进了"隐私和安全"，老教程里的路径已经对不上，按新路径找。
3. **让标签页留在后台，别每次关干净。** Chrome 的 `设置 → 系统 → 关闭 Google Chrome 后继续运行后台应用`，Edge 的"启动增强"与"睡眠标签页"都会影响回来时的重连速度。睡眠标签页会把后台页面挂起，唤醒时状态栏先转一圈，容易看成掉线。
4. **每周至少打开一次。** 41 天和 8 天那两笔记录，差别只在这里。
5. **别在多个浏览器、多台机之间轮着用同一个号。** 每次换地方都是一次新的设备授权，密集授权比长期不用更招核验。
6. **手机端保持在线。** 手机端一退，网页端跟着失效，这条没有例外。
7. **少切节点，尤其别一边发消息一边切。** 出口在几分钟内跨好几个地区，服务端只会当异常处理。

Safari 的用户要单独看一眼 `设置 → 隐私`：`阻止所有 Cookie` 打开后，表现是"登进去刷一下就弹回登录页"，看着像到期，实际是被拦，把站点加进例外比关掉整项更合适。这部分对照 [浏览器设置说明](https://tlgrqs-web.com) 里 Safari 那一节核过，路径一致。

## 重登那一次，扫码只是中间一步

很多人二维码一扫就当完事，结果半小时内又被请出来，白折腾两次。完整做法是四步：

1. 二维码出来先别急，看清页面上的刷新提示。这类码的有效期只有几分钟，放久了扫了也没反应，点刷新换一张再扫。
2. 手机端弹出的确认卡片要读一遍：设备类型、浏览器名、大致登录地点。地点对不上就取消，这一步是唯一能挡住异常登录的地方。
3. 开了两步验证的，换设备时要重填一次。别在这一步退出流程，填一半关掉，下次进来还是从头开始。
4. 进来之后回手机端设备列表，把刚才多出来的旧条目删掉。重登会生成新会话，旧的如果还在，两份并存反而更容易被判定异常。

还有一种情况要分清：如果打开页面时提示的是这台设备已被移出登录，那不是到期，是有人（或者你自己在手机端）主动终止了它。到期只需要重扫，被踢要先查设备列表再决定改不改密码。

## 记录里最意外的两个变量

一个是系统时间。有台旧机器主板电池没电，每次开机时间都往回跳，浏览器直接甩出 `NET::ERR_CERT_DATE_INVALID`，页面根本打不开。这种故障看着像登录坏了，实际连请求都没发出去，先把系统时间同步回自动再谈别的。

另一个是休眠。笔记本合盖休眠再唤醒，网页常常先显示离线状态，几十秒后才自己回来。这几十秒里如果手快点了刷新，很容易误判成掉线，然后去清数据，把本来好的会话清没了。等一分钟，比动手强。

## 把重登当成日历里的一格

三周记下来，我改了做法：不再指望它一直挂着，而是在每周固定一个时间打开一次网页版，确认还在、顺手看一眼手机端设备列表。掉线就从"突然事故"变成"迟早会发生、已经预留了五分钟"的事。

对时长这件事，预期摆正了反而不焦虑：短期用，无痕窗口最省心，用完关掉什么都不留；长期用，就守住那三个开关、别换浏览器、手机端别下线。真到期了，扫码、核对设备、清掉旧会话，四步走完，比在设置里翻半小时有用。整套流程和各类到期情形的对照，[网页版登录目录](https://tlgrqs-web.com) 里按场景分了节，遇到哪一种直接翻对应那段。
